# Operating CardReport Server

The API is deliberately unauthenticated. Restrict ingress to trusted applications;
use an internal proxy/network policy. Do not expose Swagger, metrics or report
UUID URLs to the public Internet. NetworkPolicy examples require a supporting CNI.
Chromium is the library's bundled Playwright renderer; its container launch uses
Playwright's default disabled Chromium sandbox. Container isolation and trusted
internal input are required; this is not a hostile multi-tenant rendering sandbox.

## Configuration and budgets

All settings use the `CARDREPORT_` environment prefix. `.env` is loaded only when
explicitly requested by `uv run --env-file .env ...` or the IDE. Compose reads its
own `.env` for substitutions. Secrets: `DATABASE_URL`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`.
Other required settings: `S3_ENDPOINT`, `S3_BUCKET`. `S3_PREFIX` defaults to
`cardreport/` and must be exclusive to this service installation.

least one render second; lease exceeds three heartbeats. Data/schema objects are
still materialized in the child; streaming upload is not constant-memory rendering.
Backlog admission is deliberately soft: concurrent in-flight uploads can overshoot.

## Applying configuration

All application settings in `Settings` are wired into the Compose app services.
Copy [`.env.example`](../../.env.example) to `.env` and edit the `CARDREPORT_`
values, or export them in the shell (shell values take precedence). For example:

```ini
CARDREPORT_MAX_ATTEMPTS=4
CARDREPORT_RETRY_DELAY=5
CARDREPORT_RETRY_MAX_DELAY=60
CARDREPORT_POLL_SECONDS=0.25
CARDREPORT_WORKER_CONCURRENCY=4
CARDREPORT_RENDER_TIMEOUT=450
CARDREPORT_ATTEMPT_TIMEOUT=500
CARDREPORT_SHUTDOWN_GRACE=510
CONTAINER_STOP_GRACE=520s
```

Apply with `docker compose --profile app up -d --force-recreate api worker` after
draining existing work as described below. A process reads settings at startup;
`docker compose restart` does not apply changed container environment variables.
The old Compose `WORKER_CONCURRENCY` variable remains a fallback; the prefixed
name takes precedence. In Kubernetes, put the same application keys into
`cardreport-config`, then roll out API and worker Deployments after draining.
Set `terminationGracePeriodSeconds` above `SHUTDOWN_GRACE`.

The local Compose stack intentionally keeps its bundled database/S3 endpoints and
local credentials. `.env.example`'s `CARDREPORT_DATABASE_URL`, `S3_ENDPOINT`,
`S3_ACCESS_KEY` and `S3_SECRET_KEY` are for native API debugging; Compose does not
forward those four values into containers. Container connections use service DNS,
not host loopback. Customize the manifest itself for external dependencies.
All other settings use the same prefixed names in native runs and Compose.

CardReport uses the compatible range declared in [pyproject.toml](../../pyproject.toml); `uv.lock` fixes the tested exact version.
Dependency updates are explicit and require both-engine verification; images use
`uv sync --locked`, and workers never update packages at startup.

PDF uses `min(RENDER_TIMEOUT, remaining attempt budget)` with no hidden five-minute
clamp. The attempt budget includes input preparation, rendering, upload, DB commit
and cleanup. The `4 * IO_TIMEOUT` post-render reserve is headroom for two S3 SDK
attempts, not a guaranteed total I/O deadline. The supervisor remains the backstop.
HTML does not accept a renderer timeout in the library's public API: WeasyPrint
HTML retains its internal 30-second deadline; both HTML paths remain subject to
supervisor cancellation at the attempt deadline.

Validation rejects non-finite timers and inconsistent budgets: lease must exceed
three heartbeat intervals, startup smoke must allow more than two per-engine
budgets, health age must exceed the poll interval, initial retry delay must not
exceed its cap, and lock timeout must not exceed statement timeout. Existing input
and attempt safety bounds remain visible in `Settings`; these are not extra hidden
execution deadlines. There are three total attempts by default, not three retries.

A shorter shutdown budget than the attempt budget is allowed: draining can stop
unfinished attempts, which then recover through lease expiry and consume another
attempt. Set health age high enough for the configured synchronous DB operations
(pool acquisition plus statement time, potentially twice per loop); polling alone
does not bound the duration of these operations.

Compose-only `CONTAINER_STOP_GRACE` defaults to `140s`; `WORKER_START_PERIOD`
defaults to `30s`. Increase the latter when extending startup smoke timeouts so
health probes allow startup to finish (also adjust Kubernetes startup probes).
S3 SDK retry count (two), transfer chunk sizes, ports, exit codes and schema/API
bounds remain implementation or deployment constants, not application settings.

## Worker scheduling

See [architecture and worker lifecycle](../architecture.md) for the full execution
path, ownership checks, process boundaries and recovery sequence.

A worker fills its available slots without a polling pause between claims. It
checks shutdown, leases and time budgets between claims, so filling a large worker
does not turn into one uninterrupted batch of database calls.

Attempt completion wakes the supervisor immediately, even if it happens just
before the supervisor starts waiting. SIGTERM/SIGINT and maintenance completion
also wake it. `POLL_SECONDS` controls discovery of new database jobs after an
empty queue and retries after claim errors; it does not throttle a nonempty queue
or delay replacing a finished attempt. A completion can also trigger a probe before
the previous empty/error poll interval expires. There is no database push notification,
so a job submitted to an idle worker can still wait for its next queue poll.

Supervisor waits are also bounded by heartbeat, cancellation, child cleanup and
shutdown deadlines. A high poll interval does not postpone those checks, though
individual database calls still have their documented I/O timeouts. Thread-pool
threads handle blocking database/storage work and wait for attempt processes;
actual report generation remains in a separate process per attempt.

## Failure and cleanup

Data, binding, layout, unsupported-feature and render-timeout failures are terminal.
A renderer dependency failure stops claims. Transient database/storage faults and
lost workers retry with bounded backoff and new attempt tokens. Execution is at
least once, but only the current unexpired token can commit a result pointer.

A child first unwinds the library's renderer cleanup. If it cannot stop, or crashes
with detached browser processes potentially alive, the whole worker container exits
nonzero. Container runtime cleanup kills the namespace; other slots recover by their
own leases and attempt caps. Normal SIGTERM stops claims and drains within the grace.
Workers run only in containers, with an init process and no shared PID namespace or
temporary volume. Each child receives an allowlisted environment; the supervisor
also disables Linux process dumping to protect its environment from same-UID reads.

Result expiry immediately makes download return 410, even before a cleanup tick.
Physical deletion of inputs, snapshots and output waits an additional download
timeout. Metadata has a separate minimum retention, automatically extended per job
to outlast its artifacts and download grace. Failed deletion is retried; metadata is removed only after its
objects are gone. Orphan sweeps inspect one prefix page per tick and check database
references. Keep the prefix exclusive; do not upload user files into it. There is
no public delete, cancellation or arbitrary remote-data-fetch API.

### Cleanup coordination

Each worker recovers expired leases independently, then tries a shared PostgreSQL
advisory lock for retention cleanup and one orphan scan page. A busy lock skips
cleanup without waiting; it does not pause report processing. Only one cleanup
session holds the lock at a time. Different workers can run consecutive cycles;
this is not a fixed global cleanup rate or a permanent leader.

Budget **one extra temporary DB connection per worker**, beyond `DB_POOL_SIZE`.
The dedicated autocommit connection closes after each cycle, including on errors.
It never returns a session lock to the connection pool. Use direct PostgreSQL or
session pooling; transaction pooling (for example PgBouncer transaction mode) is
not supported for workers. Session poolers must reset server sessions, including
advisory locks, when a client disconnects. The lock key `(0x43525054, 1)` is reserved for this
service across the whole database, including other search paths.

Normal disconnect or backend termination releases the lock. A silent network
partition may leave it held until PostgreSQL detects the lost client. Configure
**server-side** TCP keepalives for your infrastructure; client-side keepalives alone
do not make the server detect a vanished worker. For example, a database
administrator can configure the worker's login role (replace `cardreport` if needed):

```sql
ALTER ROLE cardreport SET tcp_keepalives_idle = 30;
ALTER ROLE cardreport SET tcp_keepalives_interval = 10;
ALTER ROLE cardreport SET tcp_keepalives_count = 3;
```

These example values apply to new PostgreSQL sessions and are operator settings,
not application defaults. Choose them for your network and any connection proxy;
they are ignored for Unix-domain sockets. With a session pooler, PostgreSQL checks
its link to that pooler; configure the pooler to detect vanished worker clients too.
An idle-session or proxy idle timeout shorter than a cleanup cycle can drop the
lock mid-cycle and allow overlapping cleanup. Choose those limits accordingly. See
[PostgreSQL TCP settings](https://www.postgresql.org/docs/current/runtime-config-connection.html#RUNTIME-CONFIG-CONNECTION-SETTINGS-TCP).
No exact recovery deadline is guaranteed. After connection loss, an old in-flight
S3 delete can still finish while a new holder runs; cleanup remains safe to repeat.

Upgrading to coordinated cleanup requires replacing all old workers: they do not
honor the new lock. No database migration is needed; follow the existing graceful
upgrade procedure. Retention settings and expiry timestamps remain unchanged.

## Observability

`/health/live` is process liveness; `/health/ready` checks database revision/storage.
Worker probes check recent supervisor progress after real PDF startup smokes for both
Chromium and WeasyPrint. If either fails, the worker claims no jobs. Both runtimes
are installed in the shared image; renderer selection is persisted per job.
API `/metrics` exposes global job counts and oldest queue age: aggregate across API
replicas with **max**, never sum. Worker port 9000 exposes per-worker active slots;
sum those across workers. Monitoring API metrics requires the client label too. Labels contain states only, never IDs, data or chart text.
CPU HPA starts at 70% of requested worker CPU; resource settings are starting values,
not throughput guarantees. Measure your own report shape and concurrency.

## Upgrade and rollback

1. Set `ADMISSION_ENABLED=false` on every API replica. Reads remain available.
2. Wait at least the upload deadline for in-flight admissions, then wait until queued
   and running counts reach zero. Retain the previous image and a database backup.
3. Stop/drain workers. For Kubernetes, confirm any previous `cardreport-migrate` Job
   completed, preserve its logs, then delete that completed Job before applying the
   migration manifest again (Jobs have immutable pod templates). Run one explicit
   migration command; never run migrations on
   each process startup. Applied migration files are immutable and forward-only.
4. Deploy matching API/worker images, check dependency readiness and reads through
   the actual proxy route (pod readiness alone is insufficient). Resume admission
   and immediately run bounded smoke reports; re-pause if the smoke fails.
5. Roll back only to an image verified against the actual database revision. An older
   exact revision gate intentionally rejects a newer schema. Otherwise keep admission
   paused and forward-fix; any offline backup restoration requires explicit approval.

Before the initial release, the development database moved through revisions 0001–0006. Revision
0003 repairs only initial synthetic-fixture digests after changing JSONB to JSON;
there was no published user-data migration. Do not reuse this repair pattern to
rewrite immutable production template versions silently.

## Stable execution error codes

| Code | Meaning / action |
| --- | --- |
| invalid_data | Correct dataset shape, types, bindings or limits |
| layout_overflow | Widen/resize the chart or use a suitable flow layout |
| unsupported_feature | Change the unsupported template feature |
| render_timeout | Reduce report complexity or raise the PDF render cap and whole-attempt budget |
| output_too_large | Reduce content or adjust the server output cap |
| input_integrity | Stored bytes differ from admission metadata; investigate storage |
| render_failed / internal_error | Terminal unexpected failure; correlate the safe `id` with logs |
| dependency_unavailable | Temporary DB/storage failure; bounded retry |
| renderer_unavailable | Worker stops claiming; repair image/dependencies |
| worker_lost | Lease expired after interruption; retry until the attempt cap |
| queue_expired | Maximum age from original submission exceeded; terminal |

### Renderer selection migration

Schema revision `0005` adds the renderer field and assigns `chromium` to existing
reports. Follow the coordinated upgrade above: pause admission, drain and stop old
workers, apply `alembic upgrade head`, then start the matching API/worker image.
The previous image expects `0004` and cannot be used as a live rollback after this
migration. Use a forward fix; do not downgrade or rewrite applied migrations.
The image installs Pango/Harfbuzz following the
[WeasyPrint Debian installation guide](https://doc.courtbouillon.org/weasyprint/stable/first_steps.html#debian-11).

## Report-history schema update

The web-console history addition introduces an index-only migration and a new
expected schema revision. Use the coordinated upgrade procedure above: pause
admission/template mutations, drain work and stop old workers, migrate explicitly,
then start matching images. Existing jobs/templates remain intact. Older images
can reject the new revision even though only indexes changed; do not assume an
automatic rollback or run a destructive downgrade.


### File input and report data upgrade

Release 0.2 adds mixed file inputs and immutable report data. Migration **0007**
adds nullable snapshot key/size/hash columns. Existing reports remain readable but
have no dataset snapshot; no data is reconstructed or backfilled.

Follow the coordinated upgrade above: pause admission, drain accepted jobs, stop
**all** API/worker replicas, run the new image's migration, then start compatible
API/workers together. Exact schema gates apply. Old workers cannot parse multipart
jobs, and old APIs cannot query the new data fields. Do not roll back only the image
after applying this forward-only migration; restore a matching backup or roll forward.

Verify a small mixed-file report succeeds, its datasets can be viewed/downloaded,
and an older result remains readable with `data_available=false`.
Snapshot storage is additional to raw uploads and output: up to 16 MiB per retained
successful report, using the result retention period and download grace. Collection
deletes data and output before marking the result deleted; transient errors retry.
Orphan sweeping recognizes committed snapshot keys and removes abandoned attempts
only after the existing grace. Failed reports have no published snapshot.

Each data view reads/parses the bounded snapshot anew. `CARDREPORT_DATA_VIEW_SLOTS`
(default 2 per API replica) limits concurrent memory use; it does not affect worker
concurrency. Busy callers receive 503/Retry-After. `DOWNLOAD_TIMEOUT` bounds view work
with checks between synchronous reads; an in-progress socket read remains bounded
by `IO_TIMEOUT`. Views verify stored size/hash and recheck expiry after parsing.


### Original files and template retention upgrade

Release 0.3 requires migration **0008**: nullable template `retention_seconds` and
report `input_files` diagnostics. Use the coordinated stop/migrate/start procedure
above; exact schema gates prohibit mixed old/new replicas. There is no image-only rollback after migration; roll forward or restore a matching
backup. Remove the retired setting from pod environments before starting new replicas.
Existing report durations,
expiry timestamps and stored bytes are not rewritten or backfilled. Old inputs can
be downloaded while still retained; their parse status is `unknown`. Already deleted
inputs cannot be recovered by the upgrade. Template definitions remain unchanged.

`CARDREPORT_INPUT_RETENTION` is retired. Remove it from deployment environments;
explicitly setting it now fails configuration validation with a migration message.
Compose no longer passes it. `CARDREPORT_RESULT_RETENTION` becomes the shared default
for newly admitted inputs, snapshots and outputs. The input default therefore grows
from one hour to **24 hours**; account for additional storage. Configure a template's
`retention_seconds` to override the default, or null to inherit it. This is captured
at admission and affects no existing job. `METADATA_RETENTION` is a minimum: the
job snapshots `max(configured minimum, effective retention + ceil(DOWNLOAD_TIMEOUT) + 1)`.
Templates/versions are not expired by this policy; archive does not delete them.

Original file objects are logical views of the existing raw upload. No duplicate S3
objects or per-file cleanup lifecycle are introduced. Parse results are bounded and
committed with the terminal attempt fence, including failures. Structural extraction
in the API never parses CSV/YAML values. Normalized snapshots remain successful-only.
All input endpoints refuse expired bytes immediately; physical deletion now allows
`DOWNLOAD_TIMEOUT` grace for inputs too. Deletion failures retry normally.

Original input operations re-read at most 16 MiB under the shared data-view limiter.
Archives are stored without compression, contain both raw request and extracted files,
and can approach 32 MiB plus bounded template/manifest/framing. Archive preparation
holds about four times the 16 MiB upload ceiling (64 MiB) per slot in Python buffers;
allow **at least 96 MiB per slot** for spools, allocator and encoding overhead, plus
upload slots and the API runtime. Default two slots fit the Compose 512 MiB limit;
raising slots requires raising the pod memory/scratch limits accordingly. A retained
32 MiB archive buffer holds its slot until delivery completes. The limiter stays held until download delivery ends;
read/preparation/delivery share one download deadline (socket reads remain bounded by
I/O timeouts). Lower admission limits do not prevent reading earlier retained uploads.


### Text substitution upgrade compatibility

When upgrading to the release using CardReport 0.9, revalidate stored templates
before resuming admission. For each revision still used by callers (including
pinned older revisions), GET `/v1/templates/{id}/versions/{version}` and pass its
`definition` to `ReportTemplate.from_dict()` using the target CardReport version.
This is a read-only check; follow paginated template/version lists to cover the
required revisions. A `TemplateError.template_path` identifies what needs editing.
`cardreport.template/1` remains unchanged, but Jinja
delimiters in report title/subtitle, card title, Text content and KPI label/note now
have meaning. Literal delimiters need raw escaping as described in the
[library contract](https://github.com/arch7tect/cardreport/blob/main/docs/user/templates.md#text-substitutions).
Create a new template revision when editing; do not rewrite stored history. No DB
migration is added for this feature. Upgrade API and workers together using the
existing coordinated procedure.
