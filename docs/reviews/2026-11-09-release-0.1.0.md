# GitHub and GHCR release setup

Date: 2026-11-09. Source baseline: `3b9c56f`. The owner authorized release automation,
Claude review, tests/documentation, and publication of CardReport Server 0.1.0.
This is source/container publication, not a production deployment or PyPI release.

## Contract

`pyproject.toml` owns the version, synchronized to `uv.lock`. Stable version bumps
on main publish after native Linux amd64 and arm64 verification. Same-version
commits and development versions do not create releases. PRs cannot publish.
The publisher consumes saved tested images, checks version/revision/platform,
pushes staging images and creates a versioned multi-platform manifest. Existing
version manifests are never replaced. GitHub receives a version tag, changelog
notes and an `images.json` digest record. See [release procedure](../releases.md).

## Consultation dispositions

Three bounded Claude consultations completed with exit 0. The focused final
review found no remaining blocker; command execution was performed separately.

Accepted and checked:

- Synchronize the lockfile and assert the installed version in each tested image.
- Verify base/dependency indexes support amd64 and arm64; all four pinned images do.
- Keep OCI labels after dependency layers. Preserve local-development defaults.
- Require explicit pull and `--no-build` for released-image Compose installation.
- Locate drafts with `gh release view`; the published-release endpoint alone does
  not find them. Reject a draft from a different commit before uploading images
  and again before publication. Asset-upload failure leaves a recoverable draft.
- Disable default build attestations for the two-platform archive/manifest path.
- Retry without overwriting a version manifest; allow replacing same-run saved
  artifacts and staging tags. Document partial state and safe patch-version recovery.
- Verify the registry-pulled amd64 image renders PDFs with both engines before
  publishing the GitHub release. Verify anonymous access after initial GHCR setup.

Kept intentionally small: Docker CLI performs registry reads instead of a custom
registry-token client. Only explicit manifest-missing errors mean absence;
authentication/network errors fail. Stale main publication fails visibly rather
than reporting a successful skip. No signing framework, extra release service,
PyPI workflow, automatic deployment or version rewriting was added.

## Verification

Unit coverage exercises version selection/conflicts, lock/changelog consistency,
lookup error handling, draft recovery/identity, failed upload ordering and existing
version identity conflicts. Lint, format, strict types, installed-wheel checks,
documentation links/examples (120 local links) and actionlint passed. Local
acceptance passed 169 tests: 75 unit, 39 PostgreSQL/S3 integration, 22 container
and 33 browser cases. The isolated successful test stack cleaned up only its own
resources. GitHub repeats the complete suite on both native architectures before
publication; the workflow run is the authoritative remote acceptance record.

The source image indexes were checked using Docker imagetools. Official references:
[GitHub runner architectures](https://docs.github.com/en/actions/reference/runners/github-hosted-runners),
[Docker multi-platform workflows](https://docs.docker.com/build/ci/github-actions/multi-platform/),
[Docker manifest inspection](https://docs.docker.com/reference/cli/docker/buildx/imagetools/inspect/),
[GHCR visibility](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry).

Raw review output and local logs stay ignored under `local/`. Tests use isolated
synthetic resources; the existing developer Compose data remains untouched.
